## 零、TL;DR：三条硬约束决定了一切

| # | Android 的前提 | 鸿蒙的现实 | 后果 |
|---|---|---|---|
| 1 | 闹钟数量几乎无限制（30 天 × 每天 N 门课 × M 档提前） | **一个普通应用最多 30 个"有效提醒"** | "30 天滚动窗口"**不能照搬**，必须改窗口算法或改提醒粒度 |
| 2 | `AlarmManager.setExactAndAllowWhileIdle` 到点唤醒**你自己的** `BroadcastReceiver` | 代理提醒到点由**系统**直接弹通知，**不回调你的进程** | `ReminderReceiver` 里的"二次校验"（`isEnabled` / `isBlocked`）**必须提前固化**成"排除日"，见 §7.2 |
| 3 | Android 12+ 要用户授权 `SCHEDULE_EXACT_ALARM`，否则退化 | 鸿蒙**没有**"精确闹钟"权限，也没有三方应用可申请的待机白名单（`deviceStandby` 公开 SDK 是空壳） | 不需要写"去授权精确闹钟"那套 UI；但准时性只能靠系统，需真机验证 |

**结论**：Android 的"逐条闹钟"要翻译成鸿蒙的"代理提醒（`reminderAgentManager`）"，
并且**用"每周重复 + 排除日"替代"30 天窗口"**，才能既绕开 30 条上限、又不依赖每日后台任务。

### 1.3 每天怎么决定响哪些课？—— 4 层过滤 + 2 层循环

原文（`ClassReminderScheduler.kt:143-178`，逐字）：

```kotlin
for (offset in 0 until horizonDays) {
    val date = today.plusDays(offset.toLong())
    // 被屏蔽的日子（法定节假日 / 校历假期 / 周末开关命中）不排提醒。
    // 补班日（调休上班的周末）在 isBlocked 里一律放行，不会被这里挡掉。
    if (HolidayManager.isBlocked(context, date)) continue

    // 调休（补课）感知：调休上班日上的是「它代替的那一天」的课，
    // 所以用 eff 的星期匹配课程、用 eff 所在的周次判断周次
    // （例如 10/11 周六补 10/8 周三 → 上的必须是第 6 周周三的课，而不是第 7 周周三的）。
    // 闹钟的**触发日期仍是 date**（那天才上课），requestCode 也仍按 date 编码，保证旧闹钟能取消掉。
    val eff = HolidayManager.effectiveDate(context, date)
    val week = weekOf(firstWeekMonday, eff)
    if (week < 1) continue
    for (course in courses) {
        if (course.dayOfWeek != eff.dayOfWeek) continue
        if (!course.occursOnWeek(week)) continue
        val slot = GltuTimeTable.byIndex(course.startIndex) ?: continue
        val start = runCatching { LocalTime.parse(slot.startTime) }.getOrNull() ?: continue

        for (m in minutesList) {
            val at = ZonedDateTime.of(date, start.minusMinutes(m.toLong()), zone)
            if (at.toInstant().toEpochMilli() <= System.currentTimeMillis()) continue
            val code = requestCode(date, m, courseSlot(course))
            val pi = pendingIntent(context, code, course, m, slot.startTime)
            try {
                am.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, at.toInstant().toEpochMilli(), pi)
            } catch (_: SecurityException) {
                am.set(AlarmManager.RTC_WAKEUP, at.toInstant().toEpochMilli(), pi)   // 降级：不精确
            }
            usedCodes.add(code); count++
        }
    }
}
```

**遍历顺序（务必照抄的语义）**：
1. 外层：日期升序（今天 → 第 30 天）
2. 中层：`courses` 的顺序 = 数据库顺序 `SELECT * FROM courses ORDER BY dayOfWeek ASC, startIndex ASC`（`CourseDao.kt:24-25`，经 `ScheduleRepository.kt:38`）
3. 内层：`minutesList` = **降序**（默认 `[30, 10]`），所以同一天的闹钟按"更早响的先排"

**过滤条件（顺序不能变）**：

| 序 | 条件 | 不满足时 | 语义来源 |
|---|---|---|---|
| ① | `!HolidayManager.isBlocked(context, date)` | `continue`（整天不排） | `HolidayManager.kt:232-253` |
| ② | `eff = HolidayManager.effectiveDate(context, date)` | — | `HolidayManager.kt:198-199` |
| ③ | `week = weekOf(firstWeekMonday, eff)` ≥ 1 | `continue` | `ClassReminderScheduler.kt:218-222` |
| ④ | `course.dayOfWeek == eff.dayOfWeek` | 跳过该课 | 用 **eff** 的星期 |
| ⑤ | `course.occursOnWeek(week)` | 跳过该课 | `Course.kt:34-42` |
| ⑥ | `GltuTimeTable.byIndex(course.startIndex)` 非空 | 跳过该课 | `TimeSlot.kt:43` |
| ⑦ | `LocalTime.parse(slot.startTime)` 可解析 | 跳过该课 | `TimeSlot.kt:26-41` |
| ⑧ | 触发时刻 `> System.currentTimeMillis()` | 跳过该档 | 过期不排 |

`isBlocked` 的真值表（`HolidayManager.kt:236-253`，注意**补班日最优先**）：

```kotlin
internal fun isBlockedPure(date: LocalDate, settings: BlockSettings, holidays: List<Holiday>): Boolean {
    // 补班日优先：即使是周末也照常上课
    if (holidays.any { it.type == HolidayType.MAKEUP && it.contains(date) }) return false
    if (settings.weekend && isWeekend(date)) return true
    return holidays.any { h ->
        h.type != HolidayType.MAKEUP && h.contains(date) && when (h.type) {
            HolidayType.STATUTORY -> settings.statutory
            HolidayType.SCHOOL -> settings.school
            // 自定义假期没有单独开关，跟随"法定节假日"那一档
            HolidayType.USER_DEFINED -> settings.statutory
            HolidayType.MAKEUP -> false
        }
    }
}
```

三个开关的默认值（`HolidayManager.kt:57-61`）：`statutory=true, school=true, weekend=false`。

周次换算（`ClassReminderScheduler.kt:218-222`，**先归一到周一**再算周差）：

```kotlin
private fun weekOf(firstWeekMonday: LocalDate, date: LocalDate): Int {
    val monday = date.minusDays((date.dayOfWeek.value - 1).toLong())
    val weeks = ChronoUnit.WEEKS.between(firstWeekMonday, monday)
    return (weeks + 1).toInt()      // 早于开学 → ≤ 0，被 `if (week < 1) continue` 挡掉
}
```

`Course.occursOnWeek` 的优先级（`Course.kt:34-42`）：**显式 `weeks` 集合 > `startWeek..endWeek` + `oddEven`**。

### 1.4 调休是怎么接进去的？—— **`date` 管"什么时候响"，`eff` 管"响哪门课"**

这是整个功能最容易被写错的地方，源码注释（`:149-152`）说得很清楚：

- **触发时刻**用 `date`（今天往后第 offset 天，真实日历日）→ `ZonedDateTime.of(date, start - m, zone)`
- **值班星期**用 `eff.dayOfWeek`（`HolidayManager.effectiveDate(context, date)`）
- **周次**用 `weekOf(firstWeekMonday, eff)`（eff 所在周的周次，**不是 date 的**）
- **`requestCode` 仍按 `date` 编码**（`requestCode(date, m, slot)`），这样下次重排时能用同一套码把旧闹钟清掉

`effectiveDate` 的实现（`HolidayManager.kt:190-199`）：

```kotlin
fun makeupRules(context: Context): Map<LocalDate, MakeupRule> =
    MakeupResolver.resolve(allHolidays(context), makeupOverrides(context)).associateBy { it.date }

/** 某天实际要上「哪一天」的课。调休日返回它代替的那一天；普通日子返回它自己。 */
fun effectiveDate(context: Context, date: LocalDate): LocalDate =
    makeupRules(context)[date]?.sourceDate ?: date
```

`MakeupRule.sourceDate` 由 `MakeupResolver.resolve` 推导（`MakeupRule.kt:89-139`，规则见文件头 `:1-25`）：
**"假期区间内被占用的工作日，从区间末尾往前取 N 个（N = 关联到该区间的调休日数量）"**，
关联优先按**假期名**（`NAME_NEAR_DAYS=21` 天），失败再按**日期邻近**（`NEAR_DAYS=7` 天），
用户手动覆盖（`makeup_overrides`）优先级最高。

> **注意**：鸿蒙侧这块已经实现好了，别重写：
> `GltuSchedule-HarmonyOS/entry/src/main/ets/data/MakeupRule.ets:327 MakeupResolver.effectiveDate(rules, date)`
> 与 `:347 MakeupResolver.decodeOverrides(raw)`。

### 1.5 什么情况下取消 / 重排？

| 时机 | 调用 | 行为 |
|---|---|---|
| 每次 `scheduleNext` **开头** | `cancelScheduledCodes(context)`（`:133`） | **先清后排**，幂等；换过"提前分钟数"也能清干净 |
| 用户**关掉提醒开关** | `ClassReminderScheduler.cancelAll(context)`（`:186-188`）← `SettingsViewModel.kt:98-105` | 只清已排的码 |
| `scheduleNext` 里 `!isEnabled` | `:134 if (!ReminderPreference.isEnabled(context)) return 0` | 清完就返回（= 关掉开关后任何一次重排都会清空） |

| 每日维护 | `:307-317` | 开关开着才续排 |

`cancelAll` 仅一行（`:186-188`）：

```kotlin

```

`cancelScheduledCodes` 的核心（`:104-120`）——**只清"上次排入的那批码"，不遍历码空间**：

```kotlin
private fun cancelScheduledCodes(context: Context) {
    val codes = loadScheduledCodes(context)
    if (codes.isEmpty()) return
    val am = context.getSystemService(AlarmManager::class.java)
    val baseIntent = Intent(context, ReminderReceiver::class.java)
    for (code in codes) {

            PendingIntent.FLAG_NO_CREATE or PendingIntent.FLAG_IMMUTABLE) ?: continue   // 不存在就跳过

    }
    saveScheduledCodes(context, emptyList())
}
```

## 二、requestCode 的编码规则

### 2.1 公式原文（`ClassReminderScheduler.kt:61-79`，逐字）

```kotlin
/**
 * 请求码：**必须包含"哪门课"**。
 *
 * 为什么：`PendingIntent` 的匹配用的是 `Intent.filterEquals`，它**不比较 extras**。
 * 如果请求码只有「日期 + 提前分钟数」，同一天同一档提醒的多门课就会共用同一个
 * PendingIntent，后一节课的 `setExactAndAllowWhileIdle` 会把前一节的闹钟**顶掉**
 * ——表现为"一天只有最后一节课会响"。
 *
 * 位分配（共 27 位，不溢出 Int）：
 *   日期 9 位（epochDay % 512，滚动窗口只有 30 天，足够唯一）
 *   课程 12 位（课程 id 取模，避免撞车）
 *   分钟 6 位（1–60）
 */
internal fun requestCode(date: LocalDate, minutesBefore: Int, courseSlot: Int): Int {
    val day = ((date.toEpochDay() % 512L).toInt() + 512) % 512
    val slot = courseSlot and 0x0FFF
    val minute = (minutesBefore - 1).coerceIn(0, 63)
    return RC_BASE + (((day shl 12) or slot) shl 6) + minute
}
```

常量（`:37-38`）：

```kotlin
private const val RC_BASE = 0x1000_0000        // 536870912
private const val DAILY_REFRESH_RC = 0x5C0_FF00 // 每日维护闹钟专用码
```

位布局：

```
 31        28 27                              6 5      0
+------------+--------------------------------+--------+
|  固定基址   |  day(9) << 12 | slot(12)       | min(6) |
+------------+--------------------------------+--------+
  0x1000_0000        27 位有效载荷，最大 0x7FFFFFF（不足 31 位）
```

| 项 | 值 |
|---|---|

### 2.4 鸿蒙：**这套编码不需要了**，但需要一个等价物

- 鸿蒙 `publishReminder` **由系统返回 `reminderId`**，不存在 `filterEquals` 撞车问题，也没有"码空间"概念。
- 但"精确取消上次排的那批"这个需求仍然存在（对应 Android 的 `cancelScheduledCodes`）：
  **不要用 `cancelAllReminders()` 一把梭**（会误杀将来可能新增的其它提醒类型）。
  建议照抄 Android 的思路：把 `publishReminder` 返回的 id 存进 preferences。
  建议键名沿用 Android：`scheduled_reminder_ids`（逗号分隔），文件就是鸿蒙版已有的 `gltu_prefs`。

```ts
// 建议新增：把 id 列表持久化，便于精确清理
private static async saveIds(ids: number[]): Promise<void> {
  await StoreHolder.instance.putString('scheduled_reminder_ids', ids.join(','));
}
private static loadIds(): number[] {
  const raw = StoreHolder.instance.getString('scheduled_reminder_ids', '');
  if (raw.length === 0) return [];
  const out: number[] = [];
  const parts = raw.split(',');
  for (let i = 0; i < parts.length; i++) {
    const n = parseInt(parts[i].trim(), 10);
    if (!isNaN(n)) out.push(n);
  }
  return out;
}
private static async cancelScheduled(): Promise<void> {
  const ids = ClassReminderScheduler.loadIds();
  for (let i = 0; i < ids.length; i++) {
    try { await reminderAgentManager.cancelReminder(ids[i]); } catch (e) { /* 已过期会抛，忽略 */ }
  }
  await ClassReminderScheduler.saveIds([]);
}
```

## 三、通知怎么发的

### 3.1 `ReminderReceiver`（`ClassReminderScheduler.kt:254-292`，逐字）

```kotlin
class ReminderReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        val title = intent.getStringExtra(EXTRA_TITLE) ?: "课程"
        val location = intent.getStringExtra(EXTRA_LOCATION)
        val advance = intent.getIntExtra(EXTRA_ADVANCE, 0)
        val startTime = intent.getStringExtra(EXTRA_START_TIME) ?: ""

        if (!ReminderPreference.isEnabled(context)) return          // ① 开关复检
        if (com.ltyksa.gltuschedule.data.HolidayManager.isBlocked(context, LocalDate.now())) return  // ② 当天被屏蔽就不弹

        val nm = context.getSystemService(NotificationManager::class.java)
        val notif = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            android.app.Notification.Builder(context, ClassReminderScheduler.CHANNEL_ID)
                .setSmallIcon(android.R.drawable.ic_menu_agenda)
                .setContentTitle("$advance 分钟后上课：$title")
                .setContentText(location?.let { "$startTime 开始 · $it" } ?: "$startTime 开始")
                .setAutoCancel(true)
                .build()
        } else { /* 同上的无 channel 版本（API < 26 兼容分支） */ }
        nm.notify((System.currentTimeMillis() % Int.MAX_VALUE).toInt(), notif)
    }

    companion object {
        const val EXTRA_TITLE = "title"; const val EXTRA_LOCATION = "location"
        const val EXTRA_ADVANCE = "advance"; const val EXTRA_START_TIME = "start_time"
    }
}
```

要点：

| 项 | 值 |
|---|---|
| extras 4 个（`pendingIntent()` 里塞，`:204-209`） | `title`=课程名、`location`=地点、`advance`=提前分钟、`start_time`=`"HH:mm"` |
| **标题** | `"$advance 分钟后上课：$title"` → 例如 `10 分钟后上课：高等数学` |
| **内容** | 有地点 `"$startTime 开始 · $location"`（如 `08:20 开始 · 3220`）；无地点 `"$startTime 开始"` |
| 小图标 | `android.R.drawable.ic_menu_agenda` |
| 自动取消 | `setAutoCancel(true)`（点一下就消失） |
| 通知 id | `(System.currentTimeMillis() % Int.MAX_VALUE).toInt()` —— **每次随机**，不去重 |
| **渠道** | `CHANNEL_ID = "class_reminder"`，名称 `"上课提醒"`，`IMPORTANCE_HIGH`，`description="在上课前提醒你"`，`enableVibration(true)`，`ensureChannel()` 在 `Application.onCreate` 调用（`:48-59`、`GltuScheduleApp.kt:29`） |

### 3.2 点击通知跳哪？—— **哪也不跳**

`ReminderReceiver` 构造 `Notification` 时**没有调用 `setContentIntent`**。
已在本机 Android 37 源码 `android/app/Notification.java` 中核实：
`Builder(Context, String)` → `Builder(Context, Notification)`（`:5131-5143`），
`build()`（`:8453-8472`）里唯一的"从 context 补字段"是

### 3.3 有没有每日维护闹钟？—— 有，凌晨 **3:30**

`scheduleDailyMaintenanceAlarm`（`:226-251`）：

```kotlin
/** 每日后台维护时间（凌晨 3:30，此时一般插着电、连着 WiFi，且不打扰用户）。 */
private const val DAILY_HOUR = 3
private const val DAILY_MINUTE = 30

fun scheduleDailyMaintenanceAlarm(context: Context) {
    val am = context.getSystemService(AlarmManager::class.java)
    val intent = Intent(context, DailyMaintenanceReceiver::class.java).apply { action = ACTION_DAILY_MAINTENANCE }
    val pi = PendingIntent.getBroadcast(context, DAILY_REFRESH_RC, intent,
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)
    val next = ZonedDateTime.now().plusDays(1)
        .withHour(DAILY_HOUR).withMinute(DAILY_MINUTE).withSecond(0).withNano(0)
    try {
        am.setInexactRepeating(AlarmManager.RTC_WAKEUP, next.toInstant().toEpochMilli(),
            AlarmManager.INTERVAL_DAY, pi)          // ← 不精确重复，省电
    } catch (_: Exception) { /* 忽略；下次打开 App 会重新排 */ }
}
```

`ACTION_DAILY_MAINTENANCE = "com.ltyksa.gltuschedule.action.DAILY_MAINTENANCE"`（`:39`）；
`DAILY_REFRESH_RC = 0x5C0_FF00`（`:38`）。**幂等**（同码 + `FLAG_UPDATE_CURRENT` 覆盖旧的）。

`DailyMaintenanceReceiver.onReceive` 干 3 件事（`:294-343`，注释是原文）：

```kotlin
override fun onReceive(context: Context, intent: Intent) {
    val pending = goAsync()                      // ← 广播接收器约 10 秒被掐断，必须 goAsync
    Thread {
        try {
            // 1) 本地且要紧的：上课提醒续排（快，且不依赖网络）
            if (ReminderPreference.isEnabled(context)) {
                val courses = AppDatabase.getInstance(context).courseDao().getAllSync().map { it.toDomain() }
                if (courses.isNotEmpty()) {
                    ClassReminderScheduler.scheduleNext(context, courses, SemesterStore.firstWeekMonday(context))
                }
            }
            // 2) 先保证自续：排下一天的维护闹钟（放在联网步骤之前，避免被网络拖没）
            ClassReminderScheduler.scheduleDailyMaintenanceAlarm(context)
            // 3) 最后才联网同步节假日。
            //    广播接收器约 10 秒就会被系统掐断，所以开一个独立线程并**硬等 6 秒**：
            //    join 超时后照常 finish()，联网线程即使还在跑也不会拖垮接收器。
            runCatching {
                if (HolidaySync.shouldSync(context)) {
                    val worker = Thread { runCatching { HolidaySync.syncBlocking(context, budgetMs = 5_000) } }
                    worker.isDaemon = true; worker.start(); worker.join(6_000)
                }
            }
        } catch (_: Exception) {
            // 忽略，下一次触发再续
        } finally { pending.finish() }
    }.start()
}
```

联网同步的判定（`HolidaySync.kt:64-84`）：从没同步过 → 同步；距上次 ≥ **7 天** → 同步；
已同步但**没有下一年数据**且当前是 **11/12 月** → 每 **3 天**重试（盯国办通知）。

## 五、`ReminderPreference` 的存储键与默认值

原文（`ReminderPreference.kt`，逐字）：

```kotlin
object ReminderPreference {
    private const val PREFS = "gltu_reminder_prefs"          // 文件名
    private const val KEY_ENABLED = "reminder_enabled"       // 键 1
    private const val KEY_ADVANCE = "reminder_advance_minutes" // 键 2

    /** 允许的提前分钟范围。 */
    const val MIN_MINUTES = 1
    const val MAX_MINUTES = 60

    /** 默认：课前 30 分钟与 10 分钟各提醒一次。 */
    val DEFAULT_MINUTES = listOf(30, 10)

    fun isEnabled(context: Context): Boolean = prefs(context).getBoolean(KEY_ENABLED, true)   // 默认 true

    /** 提前提醒分钟数（升序、去重、限制在 1–60）。 */
    fun advanceMinutes(context: Context): List<Int> {
        val raw = prefs(context).getString(KEY_ADVANCE, null) ?: return DEFAULT_MINUTES
        val list = raw.split(',')
            .mapNotNull { it.trim().toIntOrNull() }
            .filter { it in MIN_MINUTES..MAX_MINUTES }
            .distinct()
            .sortedDescending()                 // ← 实际是**降序**（注释写"升序"，注释与代码不一致）
        return if (list.isEmpty()) DEFAULT_MINUTES else list
    }

    fun setAdvanceMinutes(context: Context, minutes: List<Int>) {
        val cleaned = minutes.filter { it in MIN_MINUTES..MAX_MINUTES }
            .distinct().sortedDescending().ifEmpty { DEFAULT_MINUTES }
        prefs(context).edit().putString(KEY_ADVANCE, cleaned.joinToString(",")).apply()
    }

    /** 人类可读描述，如 "课前 30、10 分钟"。 */
    fun describe(context: Context): String = advanceMinutes(context).joinToString("、") { it.toString() } + " 分钟"
}
```

### 5.1 汇总表

| 项 | 值 |
|---|---|
| prefs 文件名 | `gltu_reminder_prefs` |
| 键 1 | `reminder_enabled`，Boolean，**默认 `true`** |
| 键 2 | `reminder_advance_minutes`，String（逗号分隔），**默认 `"30,10"`**（读取时若键不存在/清洗后为空 → 回落 `[30,10]`） |
| 取值范围 | 每个元素 **1..60**（闭区间），最多 4 个（UI 提示 `SettingsScreen.kt:550-556`："选太多会收到很多通知，建议不超过 3 个"） |
| 排序 | **降序**（`sortedDescending`），且去重 |
| 清洗（读） | `split(',')` → `trim` → `toIntOrNull`（坏值丢弃） → `filter in 1..60` → `distinct` → `sortedDescending` → 空则默认 |
| 清洗（写） | 同上，且 `ifEmpty { DEFAULT_MINUTES }` |
| UI 联动 | 改开关/改分钟数 → 立即 `rescheduleReminders()`（`SettingsViewModel.kt:93-113`） |
| UI 空选回退 | `picked.ifEmpty { ReminderPreference.DEFAULT_MINUTES }`（`SettingsScreen.kt:561-565`） |

## 七、鸿蒙移植建议（HarmonyOS NEXT / API 26）

### 7.1 能力选型：三个候选怎么选

| 方案 | 能否在 App 未运行时触发 | 准时性 | 数量/频率限制 | 是否需要额外权限 | 适合做 |
|---|---|---|---|---|---|
| **`reminderAgentManager`（代理提醒）** | ✅ 退后台/进程终止后系统代理 | 系统级，官方未承诺毫秒精度；无"精确闹钟"权限可申请 | **普通应用最多 30 条有效提醒**（系统应用 10000，整机 12000） | `PUBLISH_AGENT_REMINDER`（system_grant，声明即可）+ 通知总开关 | **上课提醒本体**（唯一正解） |
| **`workScheduler`（延迟任务）** | ✅ 有独立 Extension 进程 | ❌ 系统按内存/功耗/温度/使用习惯统一调度，**可能被延后很久** | 单应用最多 **10 个**任务；单次回调最长 **2 分钟**；按应用活跃分组**限频** | **无需权限**（API 26 权限表里没有 `WORK_SCHEDULER`） | **每日兜底维护**（续排、同步节假日），**不能**用来卡点响铃 |
| **`backgroundTaskManager`（长时任务）** | 半 ✅（要求应用在前台申请、且**必须挂一条常驻通知**） | 高 | 需 `KEEP_BACKGROUND_RUNNING`（system_grant/normal） | 有 | ❌ 不适合：上课提醒是"低频定时"，挂常驻通知会被用户骂 |

结论：
- **提醒本体 = `reminderAgentManager`**
- **每日维护 = `workScheduler` + `WorkSchedulerExtensionAbility`**（2 分钟窗口足够跑"读 DB + 重排"）
- **长时任务不要用**

### 7.2 推荐架构 A：**「每周重复骨架 + 排除日」**（绕开 30 条上限，且不依赖每日任务）

Android 的模型是"每条闹钟 = 一个 (日期, 课程, 提前档) 三元组"，30 天 × 5 门 × 2 档 ≈ 300 条。
鸿蒙只有 30 条，所以**换粒度**：一条提醒 = 一个 (课程, 提前档) 二元组。

```
ReminderRequestCalendar {
  dateTime:   { 首次响铃的日期时间 }        // 该课下一个"真要上课"的日期 - minutesBefore
  daysOfWeek: [ course.dayOfWeek ]          // 每周重复（1=周一 … 7=周日）
  endDateTime:{ 学期最后一天 23:59 }         // 到期自动停
  title:      `${minutesBefore} 分钟后上课：${course.name}`
  content:    `${startTime} 开始 · ${location}`
}
```
然后用 **`addExcludeDate(reminderId, date)`** 把"这一天不该响"的日期逐个排除。

条数从 `天数 × 课程数 × 档数` 降到 **`课程数 × 档数`**（≈ 15 门 × 2 档 = 30，正好卡在上限内；
超了就用 §7.2.3 的合并规则）。

#### 7.2.1 排除日的判定（**这是 Android 里 `ReminderReceiver` 二次校验的替代品**）

对骨架提醒的每个候选日期 `X`（X 与 `course.dayOfWeek` 同星期，且 `X ∈ [首次, endDateTime]`）：

```
要响(X) ⇔ !holiday.isBlocked(X, settings)          // ① 不是法定/校历/周末屏蔽日
        ∧ MakeupResolver.effectiveDate(rules, X) === X   // ② X 不是调休补班日（补班日另发一次性提醒）
        ∧ course.occursOnWeek(Semester.weekOf(firstMonday, X))  // ③ 该周本来就要上这门课
```
否则 → `addExcludeDate(id, X)`。

> ② 为什么必须有：调休日（如 10/11 周六）上的是"周三的课"，
> 周六的课那天**不上**。若某课 `dayOfWeek=6`，骨架会在 10/11 响 —— 错，必须排除。

#### 7.2.2 调休补班日 → 补一条**一次性**日历提醒

对每个调休日 `X`（`isMakeupDay(X)`）且 `X` 在窗口内：
取 `eff = effectiveDate(X)`，用 `eff` 的星期与周次筛课（**完全照抄 Android §1.4 的语义**），
为每门课 × 每个提前档发一条 `REMINDER_TYPE_CALENDAR`（**不带 `daysOfWeek`**，即一次性）：

```
dateTime = { X 当天的 (startTime - minutesBefore) }
title    = `${minutesBefore} 分钟后上课：${course.name}`
content  = `${startTime} 开始 · ${location}`
```
一学期调休日通常 2–8 天，条数可控；`publish` 时若报 `1700002`（超限），
按 §7.2.3 降级为"当天第一节前一条汇总提醒"。

#### 7.2.3 预算分配器（30 条怎么花）

实现一个纯函数 `allocate(budget = 30)`，按优先级分配（可单测）：

```
1. 开关关闭 / 无课程 → cancelAllReminders()，结束
2. 生成骨架候选：每个 (course, minutes) → 一条 WEEKLY 提醒
   过滤：该课在 [今天, 学期末] 内还有 ≥1 次"真要上课"的日期
3. 生成补课候选：每个调休日 → 每门课 × 每档 → 一条 ONCE 提醒（按日期升序）
4. 若 WEEKLY 条数 ≤ budget - min(ONCE 条数, 保底 4)：直接发
5. 否则按 (weekday, startIndex) 合并 WEEKLY：
   title   = `${minutesBefore} 分钟后上课：${课程名用「、」拼接}`
   content = `${startTime} 开始 · ${地点用「、」拼接}`
   合并后条数 ≈ 每天节次数 × 档数（≈ 10），预算立刻宽松
6. 仍然超 → 按"未来 30 天内实际会响的次数"降序截断（次数少的课放弃骨架，改为打开 App 时补一次性）
7. 发布顺序：先 ONCE（日期近、优先级高）后 WEEKLY；每条 publish 后记录 reminderId
```

#### 7.2.4 边界（必须处理）

| 边界 | 处理 |
|---|---|
| 学期已结束（`weekOf(today) > maxWeek`） | 不发任何提醒，`cancelAllReminders()` |
| `maxWeek` 从哪来 | `max( courses.map(c => c.weeks.length>0 ? max(c.weeks) : c.endWeek) )` |
| `endDateTime` | `firstMonday + maxWeek*7 - 1`（该周周日）的 23:59 |
| 首次 `dateTime` 已过今天 | 从"今天之后第一个满足 §7.2.1 的日期"开始 |
| 用户改了提前分钟数 | 全量重排（先 `cancelScheduled()` 再发），与 Android 一致 |
| 用户改了开学日期 | 全量重排（周次全变了） |
| 用户手动改了 `makeup_overrides` | 全量重排（`MakeupResolver.decodeOverrides` 必须传进来，见 `EntryAbility.ets:61`） |
| 节假日数据同步完成后 | 全量重排（排除日全变了）——**这是"必须重排"的又一个触发点，Android 里靠每日维护兜住** |

### 7.3 备选架构 B：**动态窗口**（= 现有实现）+ WorkScheduler 续排

即"从今天起逐天累加，直到再加一天就超过 30 条为止"（通常 2–4 天），每次打开 App 重排。
优点：逐条对应 Android，语义一一对应，改动最小（现有实现就是这个）。
缺点（必须写进已知问题）：**连续多天不开 App，窗口用尽后提醒会停**；
打开一次才续上；调休/节假日被系统"提前固化"。

若选 B，**必须**配 §7.4.6 的每日 `workScheduler` 续排，否则会漏提醒。

> 建议：**A 为主 + B 的每日 job 作为兜底**。
> 骨架把"必然要响的"覆盖住（不依赖任何后台调度），
> 每日 job 负责"补课日一次性提醒 + 排除日刷新 + 节假日同步"。

#### 7.4.2 通知渠道（**现状缺失，必补**）

Android 有 `ensureChannel()`（`IMPORTANCE_HIGH`）；鸿蒙的等价物是**通知槽位**：

```ts
import { notificationManager } from '@kit.NotificationKit';
import { reminderAgentManager } from '@kit.BackgroundTasksKit';

/** 对应 Android 的 ClassReminderScheduler.ensureChannel()。幂等，App 启动/发布前调用即可。 */
static async ensureChannel(): Promise<void> {
  try {
    await notificationManager.addSlot(notificationManager.SlotType.SERVICE_INFORMATION);
    // 只允许设置 notificationType 字段
    await reminderAgentManager.addNotificationSlot({
      notificationType: notificationManager.SlotType.SERVICE_INFORMATION
    });
  } catch (e) {
    // 已存在/内部错误都不致命
  }
}
```

依据（OpenHarmony《通知渠道类型说明》）：

| SlotType | 取值 | 分类 | 通知中心 | 横幅 | 锁屏 | 铃声/振动 | 状态栏图标 | 自动亮屏 |
|---|---|---|---|---|---|---|---|---|
| SOCIAL_COMMUNICATION | 1 | 社交通信 | Y | Y | Y | Y | Y | Y |
| **SERVICE_INFORMATION** | **2** | **服务提醒** | Y | Y | Y | Y | Y | Y |
| CONTENT_INFORMATION | 3 | 内容资讯 | Y | N | N | N | N | N |
| UNKNOWN_TYPE | 0 | 未知类型 | Y | N | N | N | N | N |

→ **必须用 `SERVICE_INFORMATION`**（"服务提醒"，全支持）；
用 `CONTENT_INFORMATION`/`UNKNOWN_TYPE` 会**没有横幅、没有铃声、不亮屏**，
用户会觉得"提醒没响"。同时提醒体要显式写 `slotType`：

```ts
slotType: notificationManager.SlotType.SERVICE_INFORMATION,
```

#### 7.4.3 发布一条周期提醒（骨架）

```ts
const req: reminderAgentManager.ReminderRequestCalendar = {
  reminderType: reminderAgentManager.ReminderType.REMINDER_TYPE_CALENDAR,
  dateTime: { year: y, month: m, day: d, hour: hh, minute: mm, second: 0 },  // 首次响铃
  daysOfWeek: [course.dayOfWeek],          // 1=周一 … 7=周日，每周重复
  endDateTime: { year: ey, month: em, day: ed, hour: 23, minute: 59, second: 0 },
  title: `${minutesBefore} 分钟后上课：${course.name}`,
  content: course.location.length > 0 ? `${startTime} 开始 · ${course.location}` : `${startTime} 开始`,
  expiredContent: `${course.name} 已经开始`,
  notificationId: NOTIFICATION_ID_BASE + index,   // ★ 不同提醒必须给不同 id（同 id 会互相覆盖）
  slotType: notificationManager.SlotType.SERVICE_INFORMATION,   // ★ 决定"响不响"
  ringDuration: 5,          // 单位 s，0=用系统通知音；设备会振动
  snoozeTimes: 0,           // 不贪睡
  tapDismissed: true,       // 等价 Android setAutoCancel(true)（默认就是 true）
  actionButton: [
    { title: '知道了', type: reminderAgentManager.ActionButtonType.ACTION_BUTTON_TYPE_CLOSE }
  ],
  wantAgent: { pkgName: AppInfo.BUNDLE_NAME, abilityName: 'EntryAbility' }   // 点击跳转（改进项）
};
const id: number = await reminderAgentManager.publishReminder(req);   // ← 返回 reminderId，存起来
```

字段语义（本机 SDK `@ohos.reminderAgentManager.d.ts` 实测）：

| 字段 | 约束 |
|---|---|
| `dateTime` | `LocalDateTime{year,month,day,hour,minute,second?}`，month 1–12 |
| `daysOfWeek` | 数组，值 1–7（周一→周日），空=不按周重复 |
| `repeatMonths`/`repeatDays` | 值域 [1,12] / [1,31]，**必须成对使用**（本项目不用） |
| `endDateTime` | 重复的结束时间（API 12+） |
| `actionButton` | **三方应用最多 2 个**；`ACTION_BUTTON_TYPE_CLOSE=0` / `ACTION_BUTTON_TYPE_SNOOZE=1` |
| `ringDuration` | 0–1800（s），默认 1；0=系统通知音 |
| `snoozeTimes`/`timeInterval` | 默认 0；`timeInterval` 最小 30s |
| `notificationId` | **同 id 后发覆盖先发** |
| `slotType` | 见 §7.4.2 |
| `tapDismissed` | 默认 `true`（点一下清除） |
| `autoDeletedTime` | 到点自动清除（ms 时间戳） |
| `groupName/groupId` | 分组；同组"不再提示"会连带取消同组提醒 |
| `customRingUri` | 铃声文件放 `resources/rawfile` |
| `fixedTimeZone` | API 26 新增，默认 `TimeZoneType.DEFAULT`（本地时区） |

**周期提醒的一个重要性质**（官方约束说明原文）：
> 当到达设置的提醒时间点时，通知中心会弹出相应提醒。若未点击提醒上的关闭/CLOSE 按钮，
> 则代理提醒是有效/未过期的；若点击了关闭/CLOSE 按钮，代理提醒过期。
> **当代理提醒是周期性提醒时，如设置每天提醒，无论是否点击关闭/CLOSE 按钮，代理提醒都是有效的。**

→ 周期骨架**不会**因为用户点了"知道了"而失效，正合适。

鸿蒙对应：

**(1) `module.json5` 注册**（`entry/src/main/module.json5` 的 `extensionAbilities` 里追加）：

```json5
{
  "name": "DailyMaintenanceAbility",
  "srcEntry": "./ets/notification/DailyMaintenanceAbility.ets",
  "type": "workScheduler",          // ★ 固定值
  "exported": false
```

**(2) ExtensionAbility**：

```ts
import { WorkSchedulerExtensionAbility, workScheduler } from '@kit.BackgroundTasksKit';
import { hilog } from '@kit.PerformanceAnalysisKit';
import { StoreHolder } from '../database/CourseStore';
import { DateUtil } from '../data/DateUtil';
import { BlockSettings, HolidayManager } from '../data/Holiday';
import { MakeupResolver } from '../data/MakeupRule';
import { ClassReminderScheduler } from './ClassReminderScheduler';

export default class DailyMaintenanceAbility extends WorkSchedulerExtensionAbility {
  async onWorkStart(work: workScheduler.WorkInfo): Promise<void> {
    // ★ 单次回调最长 2 分钟，只做"本地、快"的事：
    // 1) 续排/重排上课提醒（对应 Android DailyMaintenanceReceiver 第 1 步）
    const s = StoreHolder.instance;
    if (!(await ClassReminderScheduler.isNotificationEnabled())) { this.reschedule(work); return; }
    const settings = new BlockSettings(
      s.getBool('block_statutory', true), s.getBool('block_school', true), s.getBool('block_weekend', false));
    const courses = await s.loadAll();
    if (courses.length > 0) {
      await ClassReminderScheduler.reschedule(
        new HolidayManager(),
        MakeupResolver.decodeOverrides(s.getString('makeup_overrides', '')),
        courses,
        s.getNumber('first_monday', DateUtil.mondayOf(DateUtil.today())),
        settings);
    }
    // 2) 联网同步节假日（对应 Android 第 3 步）——鸿蒙版尚未实现，留空
    this.reschedule(work);
  }

  onWorkStop(work: workScheduler.WorkInfo): void { /* 2 分钟超时或 stopWork 时回调 */ }

  /** 重新登记下一次（Android 是 setInexactRepeating 自续） */
  private reschedule(work: workScheduler.WorkInfo): void {
    try {
      workScheduler.startWork({
        workId: work.workId,
        bundleName: 'com.ltyksa.gltuschedule',
        abilityName: 'DailyMaintenanceAbility',
        isRepeat: true,
        repeatCycleTime: 24 * 60 * 60 * 1000,   // 每天
        isPersisted: true,                       // 重启后仍有效
        earliestStartTime: 30 * 60 * 1000,       // API 22+：至少 30 分钟后才可能执行
        networkType: workScheduler.NetworkType.NETWORK_TYPE_ANY
      });
    } catch (e) { /* 忽略 */ }
  }
}
```

**(3) App 启动时登记**（对应 `scheduleDailyMaintenanceAlarm`，幂等）：

**(4) `workScheduler` 的硬约束（官方原文）**：

| 约束 | 值 |
|---|---|
| 数量 | **一个应用同一时刻最多申请 10 个延迟任务** |
| 执行频率 | 系统按 [设备使用信息统计](https://developer.huawei.com/consumer/cn/doc/) 的应用**活跃分组**分级管控，限制执行频率 |
| 超时 | `WorkSchedulerExtensionAbility` **单次回调最长运行 2 分钟**，超时不取消则系统终止 Extension 进程 |
| 调度延迟 | 系统按内存、功耗、设备温度、用户使用习惯统一调度，**资源紧张时会延后** |
| 接口限制 | Extension 内**禁止**调用 `backgroundTaskManager`、`@ohos.backgroundTaskManager`、camera、audio、media |
| 权限 | 无需 `ohos.permission.WORK_SCHEDULER`（API 26 权限定义表中**不存在**该权限） |

→ 所以：**它是"兜底"，不是"保证"**。这正是推荐架构 A（骨架自持）而不是"靠每日 job 续窗口"的原因。

### 7.5 鸿蒙限制清单（必读）

| 级别 | 限制 | 影响与对策 |
|---|---|---|
| 🔴 | **普通应用最多 30 条有效提醒**（系统应用 10000；整机 12000）；超了报 `1700002` | 决定架构：必须用"周重复 + 排除日"或"动态窗口"；发布前用 `getValidReminders().length` 自查 |
| 🔴 | **提醒到点不回调你的进程** | `ReminderReceiver` 里的 `isEnabled`/`isBlocked` 二次校验无法照搬 → 必须在**发布时**用 `addExcludeDate` 排除掉；开关关闭时要**主动** `cancelReminder/cancelAllReminders` |
| 🔴 | 未开启通知总开关时 `publishReminder` 报 **1700001**；`publish` 报 **1600004** | 首次启动调 `requestEnableNotification`；设置页给引导 |
| 🟡 | **没有"精确闹钟"权限**，无法申请待机/省电白名单（`deviceStandby` 在公开 SDK 里是空壳，属系统能力） | 删掉 Android 的"去授权精确闹钟"UI；准时性需真机（尤其深度休眠）验证 |
| 🟡 | `addExcludeDate` / `daysOfWeek` / `endDateTime` 的**条数与上限官方文档未给出** | 排除日很多（周次稀疏的课）时要实测；建议对单条提醒的排除数设上限（如 >60 就退化为按次发布） |
| 🟡 | `notificationId` **同 id 后发覆盖先发** | 每条提醒给唯一 id；或反过来利用它做"同一门课只留最新一条" |
| 🟡 | 三方应用 `actionButton` **最多 2 个** | 我们用 1 个"知道了" |
| 🟡 | 提醒的 `title`/`content` 发布时固化 | 课程改名/删课/换地点 → **必须重排**（同 Android） |
| 🟡 | `workScheduler` 单次 2 分钟、最多 10 个、按活跃分组限频、可能被延后 | 每日 job 只做本地快操作；不要依赖它卡点 |
